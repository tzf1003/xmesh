## NTFS 变更日志补读与持久游标

## 独立 guard keeper（宿主崩溃后保持目录绑定）

新增 `internal/winbox/keeper_*.go` 与隐藏子命令 `__sandbox-guard`，在 journal 与 profile 创建前启动独立 keeper 进程。keeper 以共享模式固定工作区根、祖先链和 journal 目录链，并在宿主退出后继续持有。宿主死亡后，keeper 通过仅当前用户与 SYSTEM 可访问的单实例私有命名管道允许一个恢复方接管；恢复入口为 `recoverJournalDirectoryWithKeepers`，释放入口为 `releaseCompletedKeepers`，`Hold(handle)` 可追加来源 guard。keeper 只在自行读到已绑定 journal 的持久 `complete` 记录后同意释放；同一 workspace 只允许一个 keeper；缺少 keeper 时默认失败关闭，可传入 fallback。`lifecycle_windows.go` 仅在 journal 打开后增加绑定调用。

`1f2616b` 的 [CI 38865833738](https://github.com/tzf1003/xmesh/actions/runs/38865833738) 三平台检查与 windows-native 通过。原生场景 `Test_WindowsAppContainerGuardKeeper*` 在真实 `workspaceExecution` 与 AppContainer 进程运行中强杀宿主：supervisor 回收并退出后 keeper 仍存活，工作区、祖先和 state 目录改名被拒；活动宿主期间不可接管，第二恢复方被拒，恢复方断开后可重新接管；journal 未完成时释放被拒；恢复在 keeper 保护下完成，根与文件的 DACL、控制位和标签与原值一致，journal 为 complete；恢复后 keeper 退出码为 0 且目录可改名。另覆盖 absent/complete/incomplete/unbound 释放判定、重复 keeper 拒绝、`Hold`、无 keeper 失败关闭及协议单测。

边界：keeper 只固定目录绑定，不冻结树内 ACL/reparse 写入，该约束仍属外部写入者强制约束，可通过 `Hold` 挂接；整机重启、登出或外层 Job 的 kill-on-close 会连同 keeper 一起结束，此时走 fallback 或保持失败关闭；同用户恶意进程可终止 keeper 或占用唯一接管连接；选择性对象 journal（无 workspace）不在覆盖范围；尚未接入生产启动路径（prepare 中的 `launchGuardKeeper` 与启动恢复中的 `recoverJournalDirectoryWithKeepers`）。这是真实 Windows runner 上的原生验证，生产 Windows L2 保持 `sandbox.unavailable`。

## 未知导入记录与 census 归并

此前，目录中出现未预先登记且无创建记录的对象（例如被外部移入的目录）时，USN 规划器返回无类型错误，此后每次 checkpoint（含关闭回收）均失败，已知对象的 ACL 无法回收。现在规划器把这类对象归为未知导入，journal 新增 `workspace-unknown-import` 记录并持久拥有这些身份；关闭时按当前目录树把落在未知导入目录下的剩余成员纳入。活动执行中的 checkpoint 仍以 `errWorkspaceUnknownImport` 报错，监视器照旧终止执行，重放旧游标不会使该标记消失；关闭完成后，生命周期把该类型错误返回调用方。硬链接、reparse、类型或父目录不符等证明不足的情形仍然报错；出现未知导入后不再接受新的协调导入。改动位于 `usn.go`、`usn_windows.go`、`journal.go`、`journal_import.go`、`journal_workspace_windows.go`，`lifecycle_windows.go` 仅调整 `closeContext`。

## 内核写入围栏（workspaceWriterFence）

新增 `internal/winbox/fence*.go`，以内核强制的 `workspaceWriterFence` 替代“非空 closer 即视为外部写入者已冻结”的假设。卷根到工作区、卷根到 journal 私有目录两条目录链以无 delete 共享的目录数据句柄钉住，外部 rename/delete 被内核拒绝；并对钉住的目录复核身份、类型、reparse、单链接和 DACL 字节指纹，同时读取 NTFS 变更日志——钉住对象上出现删除、改名、reparse、硬链接或安全描述符记录即判违规，改后改回原样也会被发现。违规与“无法证明未变”（日志丢失、描述符不可读）均为永久状态，仅取消不算违规。

生命周期接入：`RequireWriterFence` 选项在创建任何 journal 之前拒绝无法 Verify 的不透明 guard；准备阶段先把生命周期自己打开的目录链与围栏钉住的对象绑定为同一批，再封存工作区根描述符；准入、每个 monitor 周期、启动/导入前与清理前都会 Verify。违规时 monitor 终止全部 Job，清理仍按身份完成并把违规一并返回。改动位于 `fence.go`、`fence_windows.go`、`fence_lifecycle_windows.go`，并小幅调整 `lifecycle_windows.go`、`workspace_windows.go`（`writerCheck`）与 `usn_monitor_windows.go`（checkpoint 开头调用）。

## exec/ConPTY 托管 runner 接入与 helper 退出码 66 结论

新增平台无关接口 `internal/sandbox.Runner{Start, StartTerminal}`：托管型 runner 自行创建并清理进程，不改写 argv。`internal/policy` 增加 `UseSandboxRunner` / `SandboxRunner()`（仅 `Isolation == "L2"` 且已安装 runner 时非空），`internal/exec` 与 `internal/pty` 在存在 runner 时走托管路径（`managed.go`），否则保持原启动器路径（`launched.go`）；超时、取消和清理失败（`exec.sandbox_cleanup`）有明确语义，清理使用与调用上下文脱钩、带 90 秒上限的上下文。`internal/winbox/runner_windows.go` 与 `runner_terminal_windows.go` 的 `Runner` 每次调用建立一个完整 `workspaceExecution` 并按既有 `closeContext` 顺序回收；清理失败的执行保留并在下次准入前重试（失败即关闭），ConPTY 终端在整个执行被终止并回收后才关闭伪控制台。`WorkspaceCoordinator` 是调用方必须提供的受信 writer 边界，仓库内没有生产实现；`cmd/xmesh` 不安装 runner，Windows L2 仍返回 `sandbox.unavailable`。完整说明见[交接文档](handoff/exec-conpty-runner.md)。

退出码 66 调查（`e747cb8` 的 helper 失败）：66 是 Go race 检测器的默认退出码，数据竞争报告与运行时自身中止都返回 66。在 windows-latest 真实 AppContainer 中，含真实数据竞争的子进程容器外退出 66 并写出 `DATA RACE` 报告，容器内 3 次均退出 66 但只留下 `ThreadSanitizer: failed to restore address` 的内部中止；不含竞争的 race 构建子进程容器内 600 次中 1 次 66（`failed to allocate … error code: 487`，发生在测试代码运行之前），容器外 300 次均为 0；40 万次加锁与 256 MiB 分配各 10/10 通过；`Test_WindowsAppContainerWorkspaceDeletionRecovery` 在 race 构建下重复 25 次、两轮均通过。结论：存在两种与 `e747cb8` 一致的“66 且无可读原因”机制（race 运行时启动期固定地址映射失败，以及容器内真实竞争的报告路径被运行时中止吞掉），因 `e747cb8` 的失败日志未保留 TSan 输出，无法确定属于哪一种，也没有证据指向产品逻辑；产品二进制不使用 `-race`，只影响测试 helper。建议 helper 将 `GORACE=log_path=<相对名>` 写入已授权工作目录并在失败时输出，对“启动期映射失败”签名至多重试一次，其余 66 仍判失败（带盘符的绝对路径是非法 TSan 选项，会直接退出 66）。

## 跨主机入口 PTY 总预算（权威 Agent 租约）

此前总额只在同一主机的入口之间原子：入口把各 Agent 的快照相加，再在本机文件锁内准入，两台主机上的入口可能同时读到“还差一个”并各自创建，导致超发。现在新增可选配置 `ingress.pty_budget_authority`（一台 Agent 的设备名）。所有入口在每次 `pty.open`/`pty.transfer` 的查询、准入和调用期间持有该 Agent 托管的带围栏令牌互斥租约；总额仍由各 Agent 的实时快照得出，权威 Agent 不保存账本。

实现：`internal/pty/authority.go` 为内存互斥租约与待完成记录（`acquire`、`mark`、`release`）；`internal/role/agent/budget.go` 以 `xmesh://control/pty-budget-authority{?q}` 资源模板暴露，只对 `tag:ingress`、带 OAuth client 且获 `pty.open`/`pty.transfer` 授权者开放，所有者由认证的节点身份加进程随机数组成，策略重载立即撤销；`internal/role/gateway/pty_budget*.go` 在本机 gate 之后、文件锁之前取得租约，调用上下文截止于租约到期前 5 秒，不依赖主机间时钟，不新增对云端可见的工具。失败语义：权威离线、不可达、10 秒取不到租约或响应无效返回 `policy_denied`/`quota.unavailable`；结果不确定的调用（含持有者崩溃、租约过期）在权威侧保留待完成记录，其他入口在同一目标 Agent epoch 上拒绝新增，直到该 Agent 重启；权威 Agent 重启后一个有效期（30 秒）内不发放租约，使上一进程的租约必然失效。契约见 [CTR-GW-06](contracts/gateway.md#ctr-gw-06)，配置见 [CTR-CFG-01](contracts/config.md)，运行说明见[运维手册](operations.md)。

验证：`internal/pty` 的 6 个权威状态机用例（启动静默期、互斥与围栏令牌、待完成记录、已确认但未送达的释放、过期后晚到的释放、非法请求）；`internal/role/agent` 的授权与节点绑定用例；`internal/role/gateway` 的两个入口共享一个权威 Agent 的 5 个用例（16 个并发 open 在限额 3 下恰好准入 3 个；权威离线不创建终端；不确定调用跨入口生效且 Agent 重启后恢复；调用上下文受租约截止时间约束；未配置时保持原行为）。对照实验：临时关闭租约后同一并发用例多次出现超发（观察到准入 4 个，限额 3），带租约时 10 次 `-race` 运行通过。三平台 vet、`go test -race ./...`、契约夹具检查通过。

边界：这是进程内模拟（多个入口网关与 Agent 在同一进程，传输为内存），没有证明真实多主机、真实 tailnet 或 LAN 网络下的延迟、分区与时钟漂移行为；租约的安全性只依赖各持有者本地单调计时快于或等于权威计时，不依赖主机间时钟一致，但依赖进程时钟速率大致准确。权威 Agent 是单点：它离线时全部入口拒绝新增终端；它的内存记录不持久，重启前须确认没有结果不确定的调用。同一入口配置多个 OAuth client 时，同一进程内仍由本机 gate 串行。真实验收需要至少两台入口主机，见[验收清单](validation/2026-10-16-acceptance-checklist.md)。

`c64857c`（含跨主机预算与真实环境验收步骤）的 [push 工作流 38877354733](https://github.com/tzf1003/xmesh/actions/runs/38877354733) 与 [PR 工作流 38877359493](https://github.com/tzf1003/xmesh/actions/runs/38877359493) 的 macOS、Ubuntu、Windows 与 windows-native 检查及契约检查全部通过。同一代码的上一个提交 `32e3e43` 在 PR 工作流的 windows-native 中失败过一次：`internal/winbox` 中所有使用 `XMESH_TEST_WINDOWS_BINARY` 的 `cli-true` 子用例报 `fork/exec D:\a\_temp\xmesh-service-test.exe: The system cannot find the file specified`，说明该次运行中测试二进制在构建后被移除，失败用例与本次改动（不涉及 winbox 与 Windows 启动路径）无关；未能下载完整日志确认移除原因（可能是 runner 清理或杀毒软件隔离），换到 `c64857c` 后同类用例通过。若再次出现，应让该步骤在运行前校验二进制存在并在缺失时重新构建。

## 生产写入协调器（keeper 与内核围栏合成）

新增 `winbox.NewWorkspaceCoordinator`（`internal/winbox/coordinator_windows.go`）：每次执行先启动独立 guard keeper（固定工作区与 journal 目录链并在宿主崩溃后存活），再获取内核写入围栏，二者作为一个 guard 返回。该 guard 实现 `writerVerifier`：每次启动与导入前 `Verify` 围栏，`bindJournal` 把 journal 身份交给 keeper；`Close` 先让 keeper 在读到 journal 持久完成记录后释放，keeper 拒绝时两者都保留以便重试，之后才释放围栏。`RunnerConfig.RequireWriterFence` 使 runner 拒绝任何无法验证写入边界的 guard。

新增原生用例 `Test_WindowsManagedRunnerProductionCoordinator`（真实 keeper 加围栏，连续两次真实 AppContainer exec，核对 token、工作区内写入、工作区外读取被拒、根 descriptor 逐字节恢复、journal 无残留）与 `Test_WindowsManagedRunnerRequiresVerifiableGuard`（测试替身 guard 在要求围栏时被拒绝且已释放），随主门禁运行。

边界：`cmd/xmesh` 仍不安装 runner，Windows 生产 L2 保持 `sandbox.unavailable`。该 guard 不冻结树内写入，围栏只检出而不能阻止持有 WRITE_DAC 的同用户修改 DACL，census 仍是事后归并，普通账号读取变更日志待真实验收；因此这一步使前述各部件在同一条生产代码路径上可组合验证，并不证明安全条件已满足。
