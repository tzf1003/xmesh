# 快速安装与首次配置

桌面端和 agent 共用 `xmesh setup` 的配置计划与持久任务。安装渠道见 [安装说明](../agent/install.md)，机器操作协议见 [setup](../agent/setup.md)。Windows/macOS 是首次使用体验的交付平台，Linux 保留 CLI 能力。

## 使用流程

用途分为本机 AI、多设备和云端 AI。桌面四个页面收集用途、工作范围、连接确认和配置进度。工作目录由用户选择，设备名自动建议；开发权限允许文件读写与命令，另提供只读权限。目录策略约束工具路径，命令隔离能力由运行时政策独立决定。

本机用途使用 `serve --local-only`：内部 Agent 通过内存传输供 Gateway 调用，不开放 Agent HTTP 监听，Gateway 绑定回环地址并要求 PAT。配置保留 LAN 模式数据结构但关闭 mDNS；现有 `serve --local` 开发模式继续保留自己的语义。LAN 的 `mdns: false` 表示关闭公告与发现。

跨设备用途选择 LAN、Tailnet 或共存，并通过 xmesh 设备公钥配对建立信任。云端用途使用官方 Tailscale 与 Funnel；临时打开同一 tsnet 身份完成浏览器授权，并检查 Funnel 能力和设备域名后关闭，随后常驻服务复用身份。首次授权可能需要控制面管理员批准、允许 Funnel 及 HTTPS；应用权限由 xmesh 设备信任授予。

## 状态与恢复

`<状态根>/setup/plans` 保存批准前的配置计划；`jobs` 保存步骤与恢复收据；`backups` 保存修改前配置；`locks` 对同一节点执行跨进程互斥。凭据和原始配置文件保存在用户私有路径，公共任务结果提供状态、路径、摘要和稳定错误码。

计划包含配置和客户端文件的内容指纹。应用前、写入前及恢复时检测后续变更；过期计划要求重新预览。任务在每步前后保存进度。操作系统释放退出进程的锁，用户可以用 `resume` 继续遗留的 pending/running 任务。客户端更改先写恢复收据再替换，回滚核对任务写入的最终内容及备份指纹。

进度状态是 `pending/running/waiting_user/succeeded/failed/cancelled`。`installed`、`service_ready`、`client_verified` 分别表示服务注册、真实 MCP 健康检查、外部客户端完成验证。暂缓连接客户端的设备保留 `waiting_user`。

## 客户端与验证

首版适配 Codex CLI 的用户 TOML 配置和 Claude Code 的用户 JSON 配置。界面显示目标路径及同名条目替换提示，批准后备份并合并 xmesh 条目；其他条目保留。令牌只在主进程/Go 执行层和客户端私有文件之间传递。配置文件不合作写入者可能在最终检查与原子替换之间竞争，因此并发写入仍应先关闭编辑器或重新预览。

每个任务生成一个不创建文件的 `fs.stat` 路径挑战。用户把提示词交给实际连接的客户端执行。验证检查成功的专属工具调用及路径；云端还要求 OAuth 客户端身份，多设备还检查真实对端工具调用。健康探针从不调用该挑战，因此进程启动和内部健康检查不会替代客户端验收。

云端入口启动后，用户通过受保护字段设置登录口令，口令经 stdin 进入 Go，再通过本机 Control API 轮换。公开结果只报告已设置状态。浏览器授权入口经既有控制面来源校验后打开。

## 功能中心

基础设置后进入功能中心，提供添加设备、云端入口、MCP 工具、GitHub 运行器、工作目录与权限、网络高级设置六个入口。状态来源于当前内核、配置任务和已有页面；用户可继续进入对应功能进行配置、诊断和验证。

## 发布与后续托管服务

发布清单固定版本、通道、文档和平台产物。稳定版本需要 Windows Authenticode 和 macOS 签名、公证、装订证据；测试通道标明实际信任状态。完整离线包包含安装器、清单、平台安装包和 agent 文档。GitHub Pages 从每个发行版的文档包重建版本化站点，网站提示词指向固定版本文档。

第一阶段使用现有局域网和 tailnet 服务。后续官方托管服务复用 setup 的网络准备和入口准备边界，增加账号绑定、租户隔离、短期凭据、配额、审计、撤销及配置导出。托管服务上线属于独立项目，需要容量成本、跨租户授权和故障恢复验收；设备端仍执行目录与工具权限。当前 PR 的发布不依赖托管服务上线。
