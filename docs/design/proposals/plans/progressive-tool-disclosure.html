xmesh 工具列表渐进式披露设计

仅设计，未改代码 · 基于仓库 tzf1003/xmesh master（cf8c834）的 docs/contracts/gateway.md、docs/contracts/mcpmux.md、internal/role/gateway/gateway.go、internal/role/agent/specs.go · 2026-11-01

结论先说。列表长的根因是“设备 × 工具”的乘法：同一个 fs.read 为每台设备各登记一份。按你的方向，第一步是每个工具只列一次，用 device 参数选设备，设备数从列表长度里彻底消失，123 个工具降到 37 个。第二步才是渐进式披露：低频能力组（computer.*、将来的 browser.*、desktop.*、后端工具）不进列表，经已有的 tools.search 加一个新增的 tools.call 按需取用，列表固定在约 27 个。两步叠加，列表长度只随“工具种类”增长，不再随设备增长，也不会被新后端撑大。

1. 现状：列表为什么会越来越长

1.1 当前注册与暴露方式

  • Agent 侧。specs.go 的 buildSpecs 里固定 26 个内置工具：fs.* 13 个、pty.* 7 个、exec.* 2 个、backend.* 3 个、sys.info 1 个。启用 Computer 的设备再多 8 个 computer.*。后端（stdio MCP 服务）的工具以 <后端>.<工具> 并入，如 ida.decompile_function、计划中的 browser.*。
  • Gateway 侧。mcpmux 给每条对端工具加 <设备>/ 前缀后全量聚合进一份 tools/list。所以总数是 3 + Σ每台设备的工具数，随设备数线性增长，每台设备的 schema 重复一份。
  • 已有的缓解手段。(a) gateway.expose_backends: favorite：只列内置工具和标记 favorite 的后端工具；(b) session.set_defaults 设默认设备后，列表额外展开该设备完整工具表；(c) tools.search 能在设备的完整工具表里查，返回含 inputSchema。
  • 客户端限制。claude.ai 一类客户端只读一次 tools/list、不处理 tools/list_changed，所以首次 tools/list 要等各设备能力表就绪，最多再等 5 秒（CTR-GW-04）。列表越依赖设备状态，越容易出现“列表读早了”。

客户端还会把 home-windows/fs.read 摊平成 mcp__xmesh__home-windows_fs_read 这类名字，名字本身也占上下文。

1.3 接下来的增量

并行线程的方案要把 agent-browser、agent-desktop 作为后端接入，工具会以 <设备>/browser.* 出现，每台装了的设备都是一份。假设浏览器每台约 20 个（这是我的假设，P0 要实测），3 台设备装上就是 123 → 约 183。favorite 过滤只能整个后端“全显或全藏”，且默认关闭，解决不了“设备多 × 工具多”的乘法。

还有一个现有缺口。切到 expose_backends: favorite 后，被藏起来的工具可以用 tools.search 查到 schema，但模型没有一个工具可以调用它们：客户端只会调用出现在 tools/list 里的工具。服务端 tools/call 其实不要求工具在列表里（只做 scope 校验和在线检查），所以缺的只是一个入口。

Token 量级估算：每个工具的名字、说明和 schema 按 150 到 300 token 算，123 个工具约 2 万到 3.7 万 token，每次会话都要背着。这是粗估，P0 会直接量 tools/list 的字节数。

2. 方案总览：先去掉设备乘数，再按组披露

第 A 层：设备参数化 解决 设备 × 工具 同名工具只列一次，不带设备前缀，schema 里多一个可选的 device 参数。模型调用 fs.read {"device":"home-windows","path":"…"}。Gateway 在收到后把它改写成现有的 home-windows/fs.read，下游流水线不变。设了默认设备时 device 可省略，这与 CTR-GW-01 现有“无前缀名补默认设备”的语义一致。
第 B 层：按组披露 解决 工具种类增长 配置 listed_groups（默认 fs, exec, pty, sys）。这些组常驻列表；其余组（computer、browser、desktop、各后端）不进列表，通过 devices.list 的能力摘要得知存在，用 tools.search 取 schema，用 tools.call 调用。
元工具 永远在列表里 devices.list、tools.search、tools.call、session.set_defaults。
模式列表里的工具数（当前 4 台设备）加 1 台设备加 browser（假设约 20 个）
full（现状）123+26 到 +34每台装了的设备 +20
unified（仅第 A 层）37（3 + 26 内置 + 8 computer）0+20（一次）
unified + 第 B 层（推荐）约 27（4 元工具 + fs 13 + exec 2 + pty 7 + sys 1）00
compact（只留元工具）4，可再加 pinned00

backend.* 三个租约工具也归入非常驻组，由 search/call 取用。compact 保留给“连几十个工具都嫌多”的客户端。

典型调用链（推荐模式）

1. devices.list
   → [{"id":"home-windows","groups":{"fs":13,"pty":7,"exec":2,"computer":8,"browser":24}, ...}]
2. fs.read {"device":"home-windows","path":"C:\\x.txt"}          ← 常驻工具，直接调用
3. tools.search {"group":"browser","detail":"brief"}             ← 低频组，先找
   → [{"tool":"browser.open","description":"打开网址","devices":["home-windows"]}, ...]
4. tools.search {"names":["browser.open"]}                       ← 取 schema
5. tools.call {"device":"home-windows","tool":"browser.open","arguments":{"url":"https://example.com"}}
   → 结果与直接调用完全一致（content / isError / structuredContent / 图片块）

3. 设备参数化的细节

  • 名字。列表里是无前缀的 fs.read、exec.run 等。客户端摊平后是 mcp__xmesh__fs_read，名字也不再带设备名。
  • schema 注入。Gateway 在每个列出的工具的 inputSchema.properties 里加 device：{"type":"string","description":"目标设备名，见 devices.list；已用 session.set_defaults 设过默认设备时可省略"}。不放进 required，因为列表是静态的，而是否设过默认设备是会话状态。运行时两者都没有则返回 invalid_args，错误里带当前在线设备名，模型下一轮可直接重试。不用 enum 列出设备名，否则设备上下线就要改 schema 并发 list_changed，而 claude.ai 一类客户端不处理它。
  • 改写。在中间件最前面（审计与配额之前，见第 5 节）：若请求名无 /、不是 Gateway 自有工具，且参数里有 device，则取出 device，名字改为 device + "/" + name，从参数里删掉 device，其余字段原样转发。此后走现有的在线检查、scope、配额、审计、默认 cwd/env 注入。没有 device 时走现有补默认设备分支。
  • 参数名冲突。内置工具没有名为 device 的参数（specs.go 的参数集合里没有）。后端工具若自己声明了 device，Gateway 不对它注入，该工具改走 tools.call（显式 device 字段与工具自己的参数不冲突）。
  • 列哪些工具。列表里的工具集合 = 在线设备（及离线不足 24 小时，与 devices.list 保留期一致，减少抖动）工具表的并集，再按 listed_groups 过滤。调用方在任一设备上被 scope 允许就列出；真正调用时按目标设备再判一次，与现有 oauth.AllowsArguments(v.p.Scopes, deviceName, tool, args) 一致，所以设备级 scope 不会被绕开。
  • 版本差异。同名工具在不同设备 schema 不同（Agent 版本不一致）时，按 schema 哈希分组，列出设备数最多的那一版；其余设备照常可调，Agent 自己会按自己的 schema 校验并返回 invalid_args，search 能看到各版本。
  • 首次列表更快。内置工具的 schema 来自同一代码库的 buildSpecs，Gateway 可以用静态内置表生成常驻部分，不必再等各设备的能力表（现在要 waitOthers 最多 5 秒）。后端工具不进常驻列表，也就不再有“列表读早了”的问题。
  • 默认设备展开的旧行为。现在设默认设备后会额外展开该设备完整工具表（CTR-GW-01）。在 unified 下这条改为不再展开，因为同名工具已经在列表里、device 可省略，展开只会制造重复。

4. 元工具契约（拟）

4.1 devices.list：增加能力摘要（向后兼容）

现有字段不变，每台设备新增 groups：按工具名第一个 . 之前的部分统计数量。模型一次调用就知道“这台机器有没有浏览器、有没有桌面控制”，不用为此去搜索。backends 字段保留。

4.2 tools.search：去重、分档、可选设备

参数说明
device变为可选。省略表示在所有在线、且调用方有权限的设备上搜。
pattern沿用大小写不敏感子串，* 为全部。
group新增，按组筛选，如 fs、browser。
names新增，精确名字数组，用于一次取多个工具的 schema（取代单独的 describe 工具）。pattern、group、names 至少给一个。
detail新增，brief（名字、说明、所在设备）或 schema（再加 inputSchema）。为不破坏现有契约，指定 device 时缺省仍是 schema；省略 device 时缺省为 brief。

返回按“工具 + schema 版本”去重：{"tool":"fs.read","description":"…","schema_id":"a1b2","inputSchema":{…},"devices":["home-windows","ubuntu-aws"]}。若设备间 schema 因版本差异不同，则按 schema_id（schema 的哈希）拆成多项。4 台设备的 26 个内置工具从 104 份 schema 变成 26 份。上限：brief 200 条、schema 25 条，超出带 truncated。结果只含调用方 scope 允许的工具，规则与现在 tools/list 的 allowed 判断相同。

4.3 tools.call：新增

{"device": "home-windows", "tool": "browser.open", "arguments": {"url": "https://example.com"}}
  • device 与 tool 分开传，与第 A 层的 device 参数同一语义；device 省略则用默认设备。也接受 tool 直接写 home-windows/browser.open。arguments 缺省 {}。
  • 目标不得是 Gateway 自有工具（devices.list、tools.search、tools.call、session.set_defaults），否则 invalid_args，防止递归。
  • 语义等价于直接调用该工具。结果原样返回，不包一层，不翻译错误码，resource_busy 等照旧。
  • 自纠错提示。目标工具返回 invalid_args 时，在错误详情里附上该工具的 inputSchema（超过 8 KiB 则只附参数名与必填项），模型下一轮可直接修正，不必再搜一次。
  • 工具不存在或后端不可用：沿用 not_found，并提示用 tools.search 查名字。

5. Gateway 实现落点

核心原则：在最前面把 tools.call 改写成真实的 tools/call，之后整条现有流水线原封不动。这样鉴权、配额、审计、默认 cwd/env 注入、进度令牌、取消、drain 都不用重写。

  1. 改写位置（两种改写共用）。要改写的有两类：tools.call，以及带 device 参数的无前缀工具调用。gateway.go 中间件里，必须放在审计开始（约第 373 行）和 CheckExecTimeout/quota.Acquire（约第 392 行）之前：这两处用 call.Params.Name 做判断，若在改写之前执行，看到的会是 tools.call，配额和审计就记错了对象。改写把 Params.Name 换成 设备/工具，Params.Arguments 换成去掉 device 后的参数（tools.call 则取其 arguments），保留 _meta（含 progressToken）。
  2. 审计。记录真实工具名，另加一个 via: "tools.call" 字段。不改工具名本身（coexist CI 对审计工具名有断言）。
  3. scope。不为 tools.call 单设权限，授权完全由内层工具决定：现有 v.allowed 与 oauth.AllowsArguments 照常对真实目标生效。tools.search 过滤结果用同一判断。
  4. 默认补全。改写后名字若无 /，走现有“补默认设备前缀”分支。devices.list、tools.search、session.set_defaults 的特例分支不动。
  5. 列表生成。现有 tools/list 过滤处（约第 479 行起）按 tool_surface 分支：full 保持现状；unified 返回元工具加 listed_groups 内的去重工具（注入 device 参数，见第 3 节）；compact 只留元工具和 pinned_tools。unified、compact 下可以跳过 waitOthers，因为常驻部分来自静态内置表，不再依赖其他设备的能力表，首次 tools/list 变快，也彻底绕开“客户端只读一次列表”的问题；目标设备的能力就绪仍由 tools/call 和 tools.search 里的 waitReady 保证。
  6. search 的数据源。复用 v.down[device].tools 的缓存，在 Gateway 内存里做去重和哈希，不新增设备往返。
  7. 引导文案。在 MCP initialize 的 instructions 与三个元工具的 description 里写清流程“devices.list → tools.search → tools.call”，并说明“设了默认设备后可省略前缀”。这是模型会不会用的关键，不能省。

6. 配置与兼容

gateway:
  tool_surface: full        # full（现状，默认）| unified | compact
  listed_groups: [fs, exec, pty, sys]   # unified 下常驻列表的工具组；其余组走 search / call
  pinned_tools: []          # compact 下，在默认设备上固定展开的工具，如 [exec.run, fs.read]
  expose_backends: all      # 保留；unified / compact 下被 tool_surface 覆盖
  • 默认仍是 full，升级后行为不变；元工具的新参数全是增量。tool_surface、listed_groups、pinned_tools 走 gateway.expose_backends 同款热加载，变更时发 tools/list_changed。
  • 现有 favorite 标记在 unified / compact 下可作为常驻与 pinned 的补充来源，避免两套概念并存太久，文档里标注为过渡。
  • 按连接选择模式（可选）：允许在 MCP 地址上带 ?surface=compact|full 覆盖全局值，让同一个 Gateway 同时服务“能自己做工具搜索的客户端”和“只会读一次列表的客户端”。倾向做，但放在第二阶段。

7. 用户自己添加的 MCP 服务器

这里指的是用户在某台设备的 agent.backends 里配置的 stdio 或 http MCP 服务器，如 ida、frida，以及计划中的 agent-browser。它们已经走统一机制：Agent 启动时对每个后端做 initialize + tools/list，工具名变成 <后端名>.<工具>，再由 Gateway 加设备前缀。所以它们不需要单独的通道，就是本方案里的“一个组”，组名是第一个 . 之前的后端名。（如果你说的是云端 Agent 侧自己加的连接器，那不在 xmesh 控制范围内，xmesh 只是其中一个连接器。）

默认怎么处理

  • 默认不常驻。用户加的后端工具数量和质量不可预知（一个第三方 MCP 可能带几十上百个工具、很长的说明），所以不自动进 unified 的常驻列表，而是走 devices.list 看到、tools.search 找、tools.call 调。这样用户随便加多少后端，列表都不变。
  • 用户可以把某个后端升为常驻。现有 favorite: true 沿用为“常驻”开关（在 unified 下等价于把该后端名加进 listed_groups）。同时加一个全局上限 max_listed_tools（建议 30）：常驻工具总数超限时，按后端从大到小降回按需，并在 devices.list 和日志里报告，避免一个大后端把列表撑回去。
  • 让模型知道这个后端是干什么的。后端名（如 ida）对模型不一定自明，而按需披露依赖模型先“知道有这个东西”。所以给后端配置新增可选的 desc 字段，devices.list 的能力摘要里带出来："backends":[{"name":"ida","desc":"IDA Pro 反汇编","tools":42,"policy":"exclusive","lease":"需先 backend.acquire"}]。没写 desc 时退回到后端 initialize 返回的 serverInfo 和工具名样例。

要注意的几个点

情况处理
租约后端（policy: exclusive）tools.call 对 _lease_token 等参数原样透传，backend.acquire 本身也是普通工具，流程不变。search 结果在该后端的工具上标注“需要先 acquire”，否则模型会直接调用后撞上租约错误。
后端工具自带名为 device 的参数只影响常驻工具的 device 参数注入：这类工具不注入，强制走 tools.call（显式 device 字段不会与它自己的参数冲突）。
后端名与内置组重名（如叫 fs）组名按第一个 . 切分，会与内置 fs.* 混在一起。配置校验时拒绝与内置组同名的后端。
同一后端装在多台设备search 按 schema 哈希去重，只出现一次并列出设备；版本不同则分项。这正好受益于第 4.2 节的去重。
后端工具名含 /CTR-GW-01 规定 Agent 工具名不得含 /。第三方后端的工具名是否会被拒绝或改写，我没有核对代码，列入 P0 检查。
权限现有 scope 已有 backend:<设备>:<后端> 形式。search 和 call 都按它过滤，用户加的后端不会因为走按需通道而绕开授权。
说明文字不可信后端的 description 来自第三方，可能带提示注入。与现状一致，原样透传，不因按需披露多出新信任边界；search 不对内容做改写。
后端崩溃或重启常驻部分不受影响（它们不含后端工具）。按需部分每次 search 都读最新缓存，不需要靠 list_changed，反而比现在更可靠。

8. 风险与取舍

风险说明缓解
模型多绕一步，偶尔不会用间接调用比直接看到工具更容易出错。pinned_tools 保留热点；instructions 写明流程；invalid_args 自带 schema；上线后看 search→call 转化率。
device 参数被模型漏填或填错设备名要靠 devices.list 得知，模型可能猜名字。错误里带在线设备名；instructions 要求先 devices.list；设默认设备后可省略；上线后看该类 invalid_args 比例。
客户端按工具粒度的审批变粗unified 下常驻工具仍是逐个工具，审批粒度不变，只是不再区分设备。只有走 tools.call 的低频组（浏览器、桌面等）会合并成一个审批项，也带不了逐个的读写、破坏性注解。xmesh 的权威授权本来就在服务端（scope、策略、审计），客户端审批只是附加一层；高风险的组（如 computer）若你希望保留客户端逐次确认，可把它加进 listed_groups，代价是多 8 个工具、与设备数无关。
搜索结果泄露能力未授权的工具不应被搜出来。search 与 list 共用 allowed 和 scope 判断，不额外放宽。
schema 去重误并不同版本 Agent 的同名工具 schema 不同。以 schema 哈希区分，不同则分项列出设备。
提示注入面搜索结果里的 description 来自后端，是不可信文本。与现状相同，原样透传说明；不因搜索多出新信任边界。

9. 考虑过但不选的方案

方案不选的原因
把同类工具合并成“单个大工具 + action 参数”（如 fs {action, ...}）丢掉每个动作自己的强类型 schema，现有 specs.go 与契约测试都要重写，参数校验变弱。
每台设备一个独立 MCP 地址 / 连接器把设备选择的负担推给用户，连接器数量随设备增长，跨设备任务做不了。
只靠客户端自带的延迟加载 / 工具搜索不是所有客户端有，有的也只延迟 schema、仍列出全部名字；服务端不能依赖。可以与本方案叠加，不冲突。
只做 compact（只留元工具）每次都要多绕一步，常用的读写文件、执行命令也要先搜索，体验差。unified 让常用工具直接可见，只把低频组放到后面。
继续靠 expose_backends: favorite粒度只有“后端整体”，且藏起来的工具没有调用入口，即 1.3 的缺口。

10. 分阶段落地

阶段内容验收
P0 度量在现有 4 台设备上导出 full 的 tools/list 字节数与估算 token；实测未列出的工具能否经 Gateway tools/call 成功；确认 claude.ai、Claude Code 等客户端对 tools.call 的行为和审批表现。得到基线数字和客户端兼容表，写入 docs/validation/。
P1 纯增量tools.call、search 的 group/names/detail 与去重、devices.list 的 groups。默认仍 full。契约测试：改写后配额、审计、scope、默认 cwd/env、进度、取消都与直接调用一致；递归被拒；去重与 schema_id 正确。
P2 unifiedtool_surface: unified：列表去重、注入 device 参数、改写、listed_groups、instructions 文案、跳过 waitOthers；随后 compact 与 pinned_tools；可选 ?surface= 覆盖。列表长度与设备数无关（接入第 5 台设备后不变）；带 device 的调用在配额、审计、scope、默认 cwd/env 上与前缀调用一致；热加载时发 list_changed。
P3 接入新能力agent-browser、agent-desktop 后端不进 listed_groups，只经 search/call 暴露；后端启动参数用 --tools core 等再压一层。新增后端后列表长度不变。
P4 观察后翻默认统计 tools/list 大小、search→call 转化率、device 相关 invalid_args 率、首次任务成功率，再决定是否把默认改成 unified。指标不劣于 full。

11. 需要你拍板的点

  1. 推荐的落地形态是 unified + 低频组按需。这就是你说的“工具只列一次，调用时带设备名”，再加上把不常用的组藏起来。如果你更想先只做第 A 层（listed_groups 设成全部组，约 37 个），改一个配置即可，设计上两者是同一套机制。
  2. computer.* 要不要常驻？我的倾向：不常驻，走 search/call；想保留客户端逐次确认就加进 listed_groups。
  3. 要不要做按连接的 ?surface=？我的倾向：要，但放到 P2 之后。

以上数字里，设备工具数来自本会话实际看到的连接器列表；token 数和浏览器工具数是估算或假设，已在文中标明，P0 会实测替换。
