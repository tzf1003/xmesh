1 结论

agent-browser 作为 stdio 后端直接接入。它自带 agent-browser mcp（stdio MCP 服务），正好是 xmesh 后端机制现成支持的形态，工具会以 <设备>/browser.* 出现在 Gateway 的工具表里，不需要改协议。

agent-desktop 替换现有的桌面执行器（computer-native）。替换的是最底层的“采集与输入”，不是整个 computer 能力。Go 管理层（会话、排他租约、fencing、幂等、scope、审计、配额）、Computer Host 通道（用户 SID 管道、心跳、自启）、面板和安装流程保留，因为 agent-desktop 自己没有这些，而它们正是云端远程使用所需要的安全边界。

最大的差距已核实：agent-desktop 没有“不动鼠标的坐标点击”。它的“不打扰”指的是按 ref 的无障碍操作（不动指针、不抢焦点）和一个只用于展示的虚拟光标。按坐标点击在 macOS 上是全局 HID 事件，会移动真实指针且不恢复。所以完整替换会丢掉 xmesh 现有的像素级后台输入。依据见 5.4。建议改为：通用引擎换成 agent-desktop，macOS 保留现有后台输入模块作为坐标回退。

建议顺序：P0 对照验证 → P1 浏览器后端 → P2 桌面引擎适配器（与原生引擎并存，可切换）→ P3 macOS 默认切换 → P4 Windows / Linux 切换并删除原生执行器。

3 xmesh 里能直接复用的部分

读 docs/contracts/backend-lease.md、mcpmux.md、constraints/tools.md 与 design/19-computer.md 后，与本方案相关的现有能力如下。

  • 后端机制：Agent 把每个后端的工具暴露为 <backend>.<tool>，Gateway 再加设备前缀。stdio 后端的 command 数组直接当 argv，不经 shell。
  • 三种 policy：exclusive（需 backend.acquire 租约）、shared、per-caller（每个调用方一个进程）。UI 测试后端已在用 per-caller + process_cleanup: tree + shutdown_timeout，是最接近的先例，见 packages/ui-mcp。
  • 后端环境变量（CON-TOOL-12）：密钥类变量存在 backend-env.json（0600），不进 xmesh.yaml、不进审计和日志。适合放 AGENT_BROWSER_ENCRYPTION_KEY。
  • 结果原样透传（CON-TOOL-10）：MCP 的文本和图片内容块由 Agent 原样交给上游，浏览器截图可以直接走这条路。
  • 崩溃恢复：后端退出后指数退避重启，最多 5 次，并发出 tools/list_changed。
  • Computer：computer.* 八个工具，截图加坐标，每个交互桌面同一时刻一个控制者，动作幂等，scope 为 computer:observe|control:<device>。macOS 已有应用/窗口后台执行，复用了 open-computer-use 的 AX 与 SkyLight 配方。图形会话里的工作由 xmesh computer host 承担，SYSTEM 内核通过用户 SID 管道连接它。
现有 backends 的 scope 与审计粒度我没有逐项核对。Computer 有参数级 scope，普通后端是否能按工具名做 scope 过滤，要在 P0 查 internal/oauth 与 internal/policy。这决定第 6 节“浏览器 scope”是配置项还是需要新增代码。

4 agent-browser 接入方案

4.1 形态：stdio 后端，per-caller

云端 AgentCodex / Claude
→
Gateway / IngressOAuth + scope
→
目标设备 Agent后端 browser
→
agent-browser mcpstdio 子进程
→
daemon + ChromeCDP

配置示意（字段名以 docs/contracts/config.md 为准，实现时对照 schema 写）：

backends:
  browser:
    transport: stdio
    command: ["agent-browser", "mcp", "--tools", "core,tabs,state"]
    policy: per-caller          # 每个调用方一个进程，互不干扰
    process_cleanup: tree       # 连同 daemon / Chrome 子进程一起回收
    shutdown_timeout: 10s
    # 环境变量走本机控制通道写入 backend-env.json，不写在这里：
    #   AGENT_BROWSER_ALLOWED_DOMAINS, AGENT_BROWSER_CONTENT_BOUNDARIES=1,
    #   AGENT_BROWSER_MAX_OUTPUT, AGENT_BROWSER_ENCRYPTION_KEY,
    #   AGENT_BROWSER_IDLE_TIMEOUT_MS

选 per-caller 的原因：agent-browser 的会话、cookie 和标签页是有状态的，两个云端会话共用一个浏览器会互相覆盖页面。exclusive 会强制租约流程，对浏览器这种“每个任务一个窗口”的用法太重。

4.2 需要处理的四个问题

问题原因处理
daemon 比 MCP 进程活得久agent-browser 的 daemon 常驻，默认空闲 1 小时才退出，MCP 子进程退出后它仍在用 process_cleanup: tree；每个 per-caller 进程设独立 AGENT_BROWSER_NAMESPACE / session，避免串到别人的 daemon；把 idle timeout 调到 5 到 10 分钟。P0 验证 Unix 上 daemon 是否留在原进程组，不在的话需要后端自己的 supervisor（见 CTR-BE-01 对进程树的保证范围）
下载与文件落盘浏览器下载不经过 xmesh 的 cwd.Resolver，会绕过 allow/deny把 profile、state、下载目录固定在 workspace allow 范围内的专用目录；默认开启 download 确认或在动作策略里禁用；取回文件仍用 fs.download，保留 SHA-256 校验
有头模式与服务账户内核可能是 Windows SYSTEM 服务或无图形会话的 Linux 服务器默认无头，不需要图形会话。需要登录态/人工接管时才用 --headed，此时后端要在用户会话里跑，走第 5 节同一条 Host 通道，P1 不做
Chrome 的获取agent-browser install 需要联网下载 Chrome，设备可能在受限网络安装脚本加一步“检测 Chrome 或执行 install”；离线设备用 --executable-path 指向已装浏览器（待验证该参数）。不把 Chrome 打进 xmesh 安装包

4.3 工具暴露

用 --tools 做能力分级，不在 xmesh 里重新发明工具：

  • 默认：core,tabs，覆盖打开、快照、点击、填写、截图。
  • 需要显式开启：state（保存/加载登录态）、network、debug、react、mobile。all 不作为默认。
  • 工具名在 Gateway 里形如 home-windows/browser.<tool>。Agent 侧工具搜索（tools_search）已能按名字发现，不需要新代码。

4.4 登录态与 profile

  • 每个设备一个“工作 profile”目录，放在 xmesh 状态目录之外、workspace allow 之内，权限 0700。
  • 需要保留登录时用 state save/load，并强制设置 AGENT_BROWSER_ENCRYPTION_KEY。密钥由用户通过本机控制通道写入后端环境变量，xmesh 读接口只返回变量名。
  • --auto-connect / --cdp 连接用户正在使用的日常浏览器，等于把全部登录态交给云端 Agent，默认禁止；需要本机配置明确打开（见第 6 节）。

4.5 实时画面

agent-browser 的 dashboard（默认 4848）和 stream 只绑回环地址，不出设备。后续可在 xmesh 面板的“桌面预览”旁加“浏览器预览”，由面板经现有受保护本机通道访问。HTTP 后端必须是回环或 tailnet 地址（CTR-BE-01），这个约束天然适用。P3 再做，不阻塞主线。

5.4a 已核实：agent-desktop 的“不打扰”是什么

你看到的宣传是对的，但它说的是另一件事。我读了官网说明、CONCEPTS.md、macOS 技能文档和 macOS / Windows 的相关源码，结论如下。

路径是否动用户鼠标 / 抢焦点依据
无头（默认）：按 ref 的无障碍操作不动，不抢焦点。失败时“关闭式失败”，不会悄悄改用物理输入CONCEPTS.md：无头为“仅无障碍、无光标”，并禁止隐式抢焦点、移动光标、合成键盘、使用剪贴板
虚拟光标（cursor-overlay）只是在点击穿透窗口里画一个“Agent 光标”，不移动系统指针macOS 技能文档原话：从不移动系统指针，也不激活应用。仅用于展示
有头：按 ref 的物理点击会。先把目标窗口置前，再向校验过的点发真实点击macOS 技能文档：“Headed is physical first”；physical_click.rs 要求策略允许移动光标，并有前台门
有头：原始坐标 --xy会移动指针，但不改变焦点CONCEPTS.md；mouse_move.rs 用 HID tap 发移动事件，先偏 1 个点再到目标，没有保存和恢复原位置的代码
鼠标事件的投递方式（macOS）全局 HID tap，无按进程投递mouse/mod.rs：事件源为 HIDSystemState，按下和抬起都 post(CGEventTapLocation::HID)；检索不到 postToPid 或 SkyLight 的鼠标路径
键盘事件（macOS）有按进程投递：CGEventPostToPid，但要求目标应用已有经验证的焦点元素，并先尝试菜单快捷键和 AXConfirm / AXCancelkey_dispatch.rs
Windows没有后台输入路径。需要焦点的动作都是有头动作；SendInput 受前台门限制；PostMessage 探测后被判定不是可用输入路径（无法带修饰键）。type 无语义无头路径，无头文本走 set-valueprobes/windows/FINDINGS.md；CONCEPTS.md
多个 Agent 并发有“交互租约”，对桌面输入机器级互斥，只覆盖投递瞬间CONCEPTS.md

对比 xmesh 现有 macOS 后台输入：现有实现用 SkyLight SPI 和 Chromium 点击配方按进程投递鼠标事件，系统指针和前台焦点都不变，并已通过真实 MCP 链路验收。agent-desktop 没有等价物，它的做法是“能用无障碍就用无障碍，用不了就老实用物理输入”。

据此调整建议。完整替换会让 macOS 在“无障碍信息不足”的界面（部分 Electron、自绘控件）上，从“可后台操作”退化为“必须占用用户鼠标”。更稳妥的做法是分层：
1. 能拿到 ref 的，一律走 agent-desktop 无头路径（比坐标更稳，Windows 和 Linux 也一并受益）。
2. macOS 上没有 ref 可用时，回退到现有 Swift 后台坐标输入模块，仍然不动用户鼠标。
3. Windows / Linux 的坐标输入本来就是前台共享，直接用 agent-desktop 的有头路径，由 allow_foreground 管控。
这样 macOS 的 Rust 采集与 Windows / Linux 的原生执行器照样可以删，只留下 macOS 的一个小模块。唯一风险是上游以后若自己补上按进程鼠标投递，可再收敛。P0 里需要用真实应用实测“ref 覆盖率”，决定回退模块的优先级。

5.5 分发与授权

  • 随包分发，固定版本。agent-desktop 的二进制和它旁边的 helper 一起放进 UI 安装包与六平台归档，记录版本和 SHA-256；更新时随 xmesh 一起升级，不要求用户自己 npm install。官方 Homebrew / Scoop 还在提交中，不依赖它们。
  • macOS 授权身份。辅助功能授权按发起进程记账。把 agent-desktop 放进 app.xmesh.computer 的应用包内并随 xmesh 签名，由 Host 启动，授权就稳定地挂在 xmesh 名下。切换引擎时用户需要重新授权一次，面板的权限引导要提前说明。
  • 必须由 Host 在用户图形会话里启动。Windows SYSTEM 内核和无图形会话的服务都做不了 UIA / AX / AT-SPI，这一点与现有 Host 设计一致，不需要新机制。
  • macOS 临时目录。上游要求 TMPDIR 属当前用户且权限 0700，Host 启动时设置并检查。
  • 许可。Apache-2.0，随包附 NOTICE；vendored 的 open-computer-use（MIT）在移除原生执行器后一并删除。

  2. 并存（P2）：实现引擎接口和 agent-desktop 适配器，engine 默认 native，新工具 computer.snapshot / ref_act 仅在 agent-desktop 引擎下出现。
  3. macOS 默认切换（P3）：对照矩阵里除已接受的损失外全部通过，再把默认值改成 agent-desktop，native 作为回退保留一个版本。
  4. Windows / Linux 切换并清理（P4）：同样按矩阵验收后切换；一个正式版本无回退后，删除 computer-native、vendored 代码、native CI 工作流，并更新 design/19-computer.md、contracts/computer.md 与 schema。

6 安全与权限

两者的权限都接近“登录用户级别”。桌面一侧沿用 computer 的全部授权与审计规则，不因换引擎而放松。文件路径策略管不到浏览器和 GUI，所以需要单独的边界。

面浏览器桌面语义
scope新增 browser:control:<device>（如现有机制只能按后端名授权，则先以后端名为单位，再补参数级检查）复用 computer:observe|control:<device>，新增的 snapshot / ref_act 分别归入 observe / control
默认关闭后端不在配置里就不存在；安装向导加“浏览器”开关沿用 agent.computer.enabled，引擎由 agent.computer.engine 选择
网络范围AGENT_BROWSER_ALLOWED_DOMAINS 必须配置才启用；同时限制子资源并关闭 WebRTC可选的应用白名单（按 bundle id / exe），只允许快照和操作列表内应用
提示注入默认开启内容边界标记，把页面文本包进不可信区；MAX_OUTPUT 限制单次返回长度无障碍树里的窗口文字同样不可信，响应里加不可信内容声明
高危动作动作策略文件默认禁 eval 和 download，或要求确认；确认由本机用户完成，不由调用方参数放行密码输入框的值不返回；set-value 对密码类控件拒绝
本机介入有头模式沿用本机接管按钮并入 pause_on_user_input，检测到本机输入就撤销租约
审计记工具名、会话、URL 域名（不含路径与查询）、字节数；不记页面文本、截图、表单值记动作 ID、命令类别、ref 数量；不记快照内容和输入文本
密钥加密密钥、代理凭据只放后端环境变量无
信任边界Ingress 会经手截图与页面内容，与 computer 相同同左

8 风险与待确认

风险影响缓解
agent-desktop 是 Labs 项目，信封版本 2.5，包管理器上架尚在进行；而且它现在要承担整个桌面控制的底层接口变动、维护不确定，直接影响核心能力固定版本与 SHA-256；经 CLI 隔离，契约只声明 xmesh 自己的错误码；保留回退引擎至少一个正式版本；必要时 fork 并自行维护
坐标式后台输入在上游缺失（已核实）无障碍信息不足的应用无法在不动用户鼠标的前提下操作macOS 保留 Swift 后台输入模块作回退；P0 用真实应用量化 ref 覆盖率；上游若补齐再收敛
本机输入监测缺失pause_on_user_input 在没有监测的平台不可用Host 自建轻量监测，或明确声明不支持并拒绝该策略（与 Wayland 现状一致）
CLI 子进程延时截图和动作变慢，达不到 p95 目标P0 先测；macOS 利用上游的复用 command host；必要时改 FFI
授权需重做macOS 用户切换后要再授权一次放进 xmesh 签名的应用包；面板引导和升级说明
已验收成果作废C3 到 C8 的真机验收记录对新引擎不再适用验收脚本（accept_computer.py、Headscale 链路、DERP 强制模式）与 Go 层测试可复用；仅执行器层重新验收
daemon / Chrome 泄漏（浏览器）占资源、残留登录态process_cleanup、独立 namespace、短空闲超时
提示注入（两者）网页或窗口文字诱导越权内容边界、域名白名单、动作确认、不可信内容声明；工具层无法完全消除，文档如实说明

需要你确认的三件事

  1. macOS 是否保留现有后台坐标输入模块作为回退？核实后上游确实没有不动鼠标的坐标点击，建议保留（其余原生执行器仍可删）。不保留则 macOS 在无障碍信息不足的界面上只能占用用户鼠标。
  2. 替换是否以 P0 对照矩阵为准？建议设一个闸门：矩阵里关键项（中文输入、截图延时、Windows SYSTEM 到用户桌面）有任何一项不过，就暂停 P3。
  3. 浏览器是否需要独立 scope、是否允许连接日常浏览器？建议独立 scope、默认禁止连接日常浏览器。
